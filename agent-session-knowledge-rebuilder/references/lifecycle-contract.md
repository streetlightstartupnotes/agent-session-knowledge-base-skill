# Generated-knowledge lifecycle contract

Use this reference when the user asks to correct, withdraw, forget, expire, retain, or recheck maintained knowledge. These operations affect only the generated knowledge base. They never modify source sessions and cannot erase copies in backups, sync history, caches, exports, vendor clouds, or other devices.

## Choose the action by intent

- `retract` keeps provenance and the historical evidence trail but marks selected claims, project conclusions, feedback, rules, and relationships inactive or retracted. Use it when the record should remain auditable but must no longer guide current knowledge.
- `forget` removes selected bodies and derived records from the generated audit/review/knowledge areas, including matching private archives, and writes a content-free hashed tombstone. Use it when the generated knowledge should no longer retain the selected content.
- `schedule` records `observed_at`, `checked_at`, `recheck_after`, or `retain_until`. It does not retract or delete anything. A due or expired date creates a report item; it never triggers automatic deletion.

Do not use `forget` as shorthand for fixing one disputed conclusion when `retract` preserves the evidence boundary better. Do not claim legal or infrastructure-wide erasure from either action.

## Select an exact generated scope

At least one selector is required:

- `--source-file-id SOURCE_FILE_ID` affects generated knowledge derived from that source;
- `--event-id EVENT_ID` affects that sanitized evidence event and dependent generated records;
- `--claim-id CLAIM_ID` affects the maintained claim and dependent graph/rule material;
- `--project-key PROJECT_KEY` affects the reviewed project and its current document/relationships.

Selectors are repeatable. Resolve identifiers from the private generated audit, not from filenames guessed by the user. Report unmatched selectors; never widen a failed match to a nearby project.

## Plan before mutation

```text
<python> scripts/session_kb.py lifecycle-plan \
  --kb /approved/private/kb \
  --action retract|forget|schedule \
  --claim-id CLAIM_ID \
  --plan /approved/private/lifecycle-plan.json
```

For `schedule`, supply at least one ISO-8601 date or timestamp:

```text
<python> scripts/session_kb.py lifecycle-plan \
  --kb /approved/private/kb \
  --action schedule \
  --claim-id CLAIM_ID \
  --checked-at 2026-08-23 \
  --recheck-after 2026-11-23 \
  --retain-until 2027-08-23 \
  --plan /approved/private/recheck-plan.json
```

Planning is always read-only. It reports matched and unmatched selectors, affected events/projects/claims/rules/edges/documents, whether redistillation and retrieval gates will be required, and the source/backup warning. A private `--reason` contributes only a hash to the plan; do not assume the plaintext reason will be retained.

The plan binds the complete current generated state through `root_state_sha256` and binds its own contents through `plan_sha256`. `--plan` creates a new file exclusively and refuses to overwrite an existing plan. Keep plan files outside the public Skill repository.

## Confirm the exact impact, then apply

Running apply without `--commit` is still dry-run and returns the plan:

```text
<python> scripts/session_kb.py lifecycle-apply \
  --kb /approved/private/kb \
  --plan /approved/private/lifecycle-plan.json
```

Only after the user has confirmed that exact matched scope and impact may the Agent add `--commit`:

```text
<python> scripts/session_kb.py lifecycle-apply \
  --kb /approved/private/kb \
  --plan /approved/private/lifecycle-plan.json \
  --commit
```

Apply takes the normal knowledge-base mutation lock. If any generated file changed after planning, it fails closed and requires a new plan. Do not edit a plan to bypass that state check. Symlinked or escaping generated paths also fail closed.

## Transactional commit and recovery

A committed lifecycle operation is recoverable rather than a sequence of unrelated writes:

1. The implementation creates the private control files `audit/lifecycle-transaction.json` and `audit/lifecycle-staging/<plan-sha256>/*.stage` inside the generated knowledge base. The journal contains control metadata, not selected bodies. Staged files contain final generated bytes; for `forget`, staging fails if selected private body literals remain.
2. Before changing any live knowledge body, completion is atomically changed to `status: lifecycle-applying`, `lifecycle_transaction_pending: true`; publication and retrieval gates and their bound profile/report/manifest hashes are cleared. Reader, registration, and rebuild/incremental entrypoints fail closed while the journal exists.
3. The content-free tombstone is committed before other live writes or deletions. This lets a later rebuild suppress the selected source/record locations even if a later write is interrupted.
4. Other writes and deletions follow. The final staged completion report is written last, so a Reader cannot observe a final state while the knowledge body is only partly changed.
5. On success, staging and the journal are removed. If an atomic write is interrupted after staging, rerun `lifecycle-apply --commit` with the exact same unchanged plan. The command resumes or finishes cleanup and reports recovery. A different plan, a new planning request, registration, or rebuild is refused until the pending transaction is resolved.

Do not manually remove an active or ambiguous journal/staging directory. Inspect the pending plan hash and resume with its original private plan. If the journal is in an incomplete `preparing` phase, the implementation discards incomplete staging and asks for the same plan to be retried; it does not silently accept a different plan.

## What each committed action leaves behind

### Retract

The evidence body remains available for provenance. Selected claims become `retracted`; selected feedback is retracted; affected rule evolutions become rejected/failed; affected relationships are removed or rejected; selected current document sections and graph nodes are deactivated. The publication and retrieval gates are invalidated, because the previous manifest attested to different current knowledge.

### Forget

Selected content is scrubbed from surviving generated JSON, JSONL, Markdown, review files, current knowledge, matching private archives, and derived relationships. Selected project documents may be removed. A minimal tombstone keeps only hashed selector/affected identifiers and hashed source-record locators; it must not retain the forgotten plaintext or raw identifiers.

Tombstones participate in later rebuilds so an event at the same source/record location is not silently reintroduced even when its content changed. They do not reach back into source sessions. If the user later wants to reverse a forget, treat that as a new explicit request and explain that generated plaintext may need to be re-derived from the still-existing source or backup.

### Schedule

Scheduling writes lifecycle policy/date fields and leaves the current publication gates unchanged. It does not prove that a recheck occurred. Use the due command to find work whose recheck or retention boundary has arrived:

```text
<python> scripts/session_kb.py lifecycle-due --kb /approved/private/kb --as-of 2026-11-24
```

The due report includes selectors and dates but no claim body. `retention_expired` is a prompt for a user decision, not automatic authority to forget or delete.

## Restore a trustworthy publication after retract or forget

Committed `retract` and `forget` set graph/index state to `lifecycle-pending-redistill`, completion to `needs_redistill`, clear the verified `retrieval_profile`, suite/report/manifest hashes, and invalidate both legacy and v0.5 retrieval gates. Reopen whatever the validator identifies as affected, then run:

```text
<python> scripts/session_kb.py validate-review --kb /approved/private/kb --review REVIEW.json
<python> scripts/session_kb.py distill --kb /approved/private/kb --review REVIEW.json
<python> scripts/session_kb.py verify-retrieval --kb /approved/private/kb --eval-set /approved/private/retrieval-eval.json
```

Do not register or use the Reader while lifecycle state is pending. At handoff report the action, exact generated scope, tombstone or policy id, whether sources changed (`false`), whether backup erasure is guaranteed (`false`), gates reopened, and any unmatched selectors or remaining external copies.
