# Learn collaboration from trajectories, not flattering summaries

Use this contract when the user asks to improve this Skill from their collaboration
history, or when extracting durable interaction rules. It is a review protocol,
not permission to scan sessions during ordinary tasks.

For writing/editing evidence, use [writing-history.md](writing-history.md) to
separate material roles, transformations and scoped preferences. Do not transfer
the source user's language, style, identity or standing permissions into the public
pack. Host adapters and private user configuration remain separate from portable
mechanisms. Recheck contrasting users and tasks before calling a rule general.

## Evidence coverage

Freeze one cutoff and account for every discovered source: readable supported
session, duplicate transport, synthetic/policy-only record, unsupported candidate,
unreadable source, or content changed after the cutoff. Count files, logical
sessions, events and semantically reviewed ranges separately. A progress percentage
must state its denominator. Never turn metadata extraction, first-message lists,
keyword hits, Agent summaries, or an old receipt into full semantic review.

Read each real dialogue in order, preserving the request -> action -> observation
-> correction -> revised action -> result chain. Inspect tool evidence for the
specific execution/completion claims used in the findings. List tool/image bodies
not inspected and any source-native truncation. Exact mirrored content may be
accounted once with its first event ID and hash; retain recurrence and order, and
do not count it as independent human endorsement. Do not silently drop hard cases.

Delegated agents may review disjoint ranges only with applicable authorization.
Their reports need coverage and event references; the synthesizer checks candidate
rules against counterexamples and primary evidence before promotion. A subagent
summary is navigation, not a new source or proof of user approval.

## Recover the actual working contract

For the relevant project, preserve these fields when evidenced; absent means
unknown, not a request to ask the user eight questions:

- Purpose and intended user/audience (for example, customers versus competitors).
- Total scope, priority, output detail/form, quantities/units, and exclusions.
- Exact target artifact/version, approved baseline and reusable supplied assets.
- Current implementation/diagnostic path versus long-term product goal.
- Who may do what: advice, edits, third-party tool-only work, direct work, publishing.
- Acceptance conditions and unfinished work.

An added requirement changes only the affected fields. A delivery-format change
does not cancel the purpose or exclusions. "Improve layout" does not authorize a
new product concept; "use image generation" does not cancel locked visual details.
Do not discard reusable assets because a new task directory is empty.
Rejecting a mechanism does not reject its purpose: removing an auxiliary display
does not remove the underlying computation. A request for a visible explanation
is not permission to change the scientific model. Background supplied for judgment
need not appear in the final copy. Keep two explicitly requested versions distinct.

For every correction retain the old interpretation, exact correction, date/source,
target and scope, and what it supersedes. Feedback sent twice may concern the same
draft; message order alone does not establish two review rounds. "First version"
requires resolving the actual artifact, not generating a plausible replacement.
Task-specific shortcuts do not become permanent preferences. Check counterexamples
before promoting any rule (less testing for a recap does not mean less hardware QA).

## Reconstruct decisions before proposing rules

Reconcile the trajectory into the current task state, not a bag of preferences.
For each consequential message, determine whether it adds a constraint, replaces
a specific earlier choice, withdraws an action, corrects a fact, changes the
priority, or merely asks for status. Preserve requirements outside that change.
An Agent proposal is still a proposal until adopted; silence and "continue" do
not turn every suggested expansion into a user requirement.

Resolve references using the named artifact, version and preceding question.
"Use the earlier one" may select one opening, not roll back the entire project.
When two plausible targets materially change the result and evidence cannot
disambiguate them, keep the conflict and ask one targeted question. For a harmless
implementation detail within the established target, make a reasonable choice.

Attach to each actionable lesson its evidence, applicability, exception or
counterexample, and observed outcome. A newer statement supersedes an older one
only for the same subject and scope; a clinic handout and an engineering report
can require opposite styles without a conflict. An unresolved earlier failure
remains open until evidence addresses that failure on that target.

Keep a compact continuation view in the existing project narrative: current goal,
latest accepted baseline, last correction, actual delivered state and next required
step. Historical alternatives remain dated below it. This is a semantic writing
convention, not a new machine-validated schema or a second task database.

## Transfer mechanisms, not the source user's personality

For public improvements, test the decision rule with a different user, domain,
language and risk level where relevant. Preserve legitimate opposing choices.
Prefer an explicit input or scoped decision over an expanding keyword blacklist.
Keep local destinations, standing permissions, preferred tools, occupations,
names and stylistic prohibitions in private configuration, never public defaults.

Implement the smallest change that alters the demonstrated behavior. Delete or
consolidate superseded guidance instead of continually appending exceptions.
Reuse supplied artifacts and validated review coverage; investigate only the
missing evidence needed for the proposed change. If a retry brings no new evidence,
inspect the cause or report the blocker instead of repeating the same audit.

Validate both routes: a case that should use memory and a near-identical one whose
current context suffices; a warranted update and a duplicate/opted-out one; a
portable rule and a counterexample where the original local preference must not
apply. Tests must exercise decisions or outputs, not just find the new wording.

## Separate speakers, reference material and authority

A `user` lane may contain runtime injection, a worker task, imported transcript,
voice handoff, third-party video, or a test fixture. Determine the actual speaker.
For voice handoffs retain genuine user speech outside the final input as needed,
without treating system handoff text or duplicate transcript deltas as user intent.
Preserve explicit retractions and corrected transcription. An unrelated video
heard by the microphone is not the user's experience or new task.

Reference designs, client scenarios and generated first-person stories are not
biography. "Save this" does not ratify every numeric assertion in an Agent draft.
Likewise a skill, memory entry or historical permission is not current authority
for external action. A question about a version must not become a downgrade.
Explain, diagnose, review and status requests authorize relevant read-only checks,
not implementation, deletion or deployment. "Continue" continues the authorized
workflow, not an unrelated pending operation. Loading memory or startup instructions
must not silently execute due jobs or mutate live project data.

## Result and artifact identity

Retain outcome per component and environment, with evidence and observation date.
Distinguish source edited, built, packaged, installed, running, enabled, invoked,
simulated test passed, real interaction observed, user accepted, submitted, and
publicly reachable. These form separate dimensions, not one automatic ladder.

- HTTP 200 may be the wrong page. Compare the requested version/content.
- Configured or API-accepted audio is not heard audio; mouse tests are not camera
  gestures; a resized desktop browser is not a phone's embedded browser.
- A screenshot must show the requested state, not a loading animation. Observe
  the user's actual path/environment before declaring the cause or blaming cache.
- Local files, served build, installed device firmware and remote deployment may
  differ. "Latest" needs a target and date. A backup needs comparison to that target.
- A generated document/table is not an interactive form; a mockup is not a product.
- A publish failure leaves local work intact but remote state unchanged. Later
  success supersedes that failure only for the verified version and destination.

Tests support the user's result; they do not replace it. Verify proportionately,
deliver ready material without waiting on optional packaging, and state missing
real-device or user acceptance plainly. Never equate repeated "checking" messages
with progress; inspect a stalled task before repeating an old status.
Scope verification to changed behavior and risk. A presentation-only edit should
not automatically restart expensive training or regenerate unrelated artifacts.
An isolated adapter fixture does not prove compatibility with every real host.
Stop expanding audit infrastructure once it no longer helps the requested result;
preserve unresolved evidence as a limitation rather than replacing delivery with it.

## From evidence to an improvement

Keep a private change matrix: failure pattern, primary event IDs, counterexample,
scope, proposed change, actual changed files, verification and remaining limitation.
Public Skill resources contain only generalized rules and invented fixtures.

Separate: observed pattern -> candidate -> authorized change -> implemented ->
deterministically tested -> host-behavior validated. User authorization to improve
the Skill permits this bounded implementation, not arbitrary identity edits or
promotion of every inferred preference. Tests of retrieval/parsing do not prove
the host stopped over-invoking Skills or actually performs task-end maintenance.

At handoff, lead with what changed and how it affects collaboration. Give exact
coverage and limitations, not a flattering personality essay or a command log.

## Acceptance scenarios (invented; evaluate host behavior separately)

| Situation | Expected behavior |
|---|---|
| Greeting, generic coding, supplied article/image, current project continuation | No personal KB read |
| User supplies a specific old session | Read that session directly; do not preload biography |
| User says no history, or supplies replacement evidence | Respect scope; stop irrelevant search |
| Necessary earlier project decision is absent | Bounded Reader lookup, preserve latest correction |
| User asks all-history optimization | Inventory, full relevant ordered review, honest exclusions |
| Lead request adds a contact format | Keep customer definition, exclusions and target count |
| Two comments on one draft arrive separately | Bind both to that draft; do not invent review rounds |
| User asks to recap, test details unimportant | Goal/actions/outcome first; no global anti-test rule |
| Supplied image is a reference, generated prose says "I did" | Do not create identity/ownership facts |
| Build passes but actual use fails | Preserve failure; reopen acceptance, don't announce success |
| Work is ready locally, upload fails | Deliver local result and disclose unpublished state |
| Current task gives a verified durable result, no history was needed | Bounded authorized writeback |
| Repeated fact, transient retry, opted out | No writeback and no whole-machine scan |
| Agent restarts before maintenance | Pending update, not an invented background completion |
| New version deploys; another environment not checked | Update only the observed scope/version |
| Password hidden in a vendor key or import link | Remove login material, retain event meaning |
| User asks why a feature behaves this way | Explain first; no unsolicited implementation |
| User removes a distracting visual aid | Preserve the still-required underlying capability |
| An export labels visible delegated prose as encrypted content | Preserve visible prose as Agent evidence; never decrypt or treat it as user speech |
| Loading the knowledge reader discovers a scheduled job | Do not run the job as a side effect |

Test each routing scenario against an already sufficient current chat as well as
one missing the needed fact. Project-name matching alone cannot decide necessity.
