# Agent Session 知识库重建 Skill

把不同 Agent 留下的 session，重建成一套能追溯原话、能继续维护、能按任务调用的个人、项目和协作知识库。

当前版本：v0.4.0 Beta

## 直接复制这句话给 Agent

> 请使用 `$agent-session-knowledge-rebuilder`：先只读探查当前环境中可合法读取的 Agent session，分别报告已识别格式、未知格式、安装线索和扫描缺口；再向我确认私人知识库的保存位置，冻结本轮读取范围，清理隐私与二进制，隔离摘要、运行时注入、旧记忆和嵌套转录，把记录统一成可追溯事件；随后逐段读完每条真实项目链，核对说话人身份，保留目标变化、纠正、动作、失败、验证、交付层级和未完成项，完成证据约束的对话蒸馏；再从两端原始事件验证项目关系，建立有方向且可返回的双向连接；把反馈先记录为有限范围的候选规则，只有满足批准或重复证据门、版本记录和后续行为验证后才标记为已进化；语义发布后完成相关任务命中与无关任务 `no_match` 两道机器检索门，只有通过后才认定知识库完成，并询问我是否注册给 `$agent-knowledge-reader` 按任务读取。原始 session 始终只读，未知格式必须明确报告不支持，不得声称兼容所有 Agent 或所有系统。

除了知识库保存位置、额外权限和无法由证据解决的重大歧义，普通解析、清理、复核、连接和验证由 Agent 继续完成。

## 这套东西由两个 Skill 组成

| Skill | 什么时候用 | 做什么 |
| --- | --- | --- |
| `$agent-session-knowledge-rebuilder` | 第一次建库，或以后有了新 session | 找记录、识别格式、清理、去重、合并项目链、蒸馏、连接、增量更新、语义发布与最终检索验证 |
| `$agent-knowledge-reader` | 知识库已经完整发布，开始一个新任务 | 只读取当前任务需要的少量知识和有限确认连接；没有可靠匹配就返回 `no_match` |

Rebuilder 负责“把历史变成知识”，Reader 负责“用多少读多少”。两者分开，避免每次把整套知识塞进上下文。

## 整体逻辑

```text
只读探查 session
  → 用户确认私人保存位置
  → 冻结本轮文件与字节边界
  → 识别格式并统一成事件
  → 隐私清理、二进制剥离、噪声隔离、去重
  → 核对身份并重建真实项目链
  → 逐项目完成对话蒸馏和完成层级判断
  → 从关系两端取证并生成双向导航
  → 从反馈产生有范围、有版本的规则候选
  → 校验、蒸馏并生成语义发布结果
  → 通过正向命中和负向 no_match 检索门
  → 认定本轮完成
  → 可选注册 Reader
  → 下次只处理变化并复用仍有效的语义结果
```

## 各个功能分别是什么

| 功能 | 实际做什么 | 防止什么问题 |
| --- | --- | --- |
| 自动发现与显式路径 | 检查已知数据位置、环境配置、Agent 特征目录和用户指定的导出或根目录，并报告真实扫描分母 | 找到一个目录就误称“已经读完本机所有 Agent” |
| 适配器识别 | 每种格式由独立适配器根据文件和内容特征打分；无法唯一识别就进入未支持报告 | 把未知格式硬套成已有格式，悄悄读错 |
| 统一事件 | 把用户消息、Agent 正文、工具调用/结果、补丁、浏览器/设备事件、状态、错误和交付变成同一结构，并保留事件 id 与来源位置 | 不同 Agent 的记录无法一起复核或引用 |
| 噪声隔离 | 压缩摘要、系统或运行时注入、旧记忆读取、隐藏推理、导入转录、嵌套审批和委派包装只进排除审计 | 把上一轮摘要或别人的话当成新事实 |
| 身份归属 | 原生 `user` 通道只表示“记录里叫 user”，仍需结合会话所有者、上下文和跨事件证据，把本人、未知用户、客户、第三方、测试角色、编排者和子 Agent 分开 | 把客户提示、测试台词或子 Agent 写成用户本人 |
| 隐私与二进制处理 | 清理复合/通用凭据字段、授权头、Cookie 与 Cookie jar、URI 用户信息、私钥、联系方式、私人网络地址和不同机器的用户目录；标准/Base64URL、MIME 换行块、参数化 data URL 与二进制字段只留安全占位 | 知识库或公开代码泄露隐私、凭据和原始二进制 |
| 去重与续接 | 消除同一事件在多条传输通道里的重复表示；用原生续接关系、稳定项目 id、具体产物和用户意图提出项目链，再做语义复核 | 重复内容被当成“多次证据”，或多个项目被错合并 |
| 冻结与增量读取 | snapshot v2 为每个来源保存完整冻结摘要并独占创建；增量只把新尾部送进解析器，但仍读取旧前缀做完整性校验，统计分开记录解析字节与完整性读取字节 | 中间内容被改写、ABA 式恢复外观、旧快照覆盖，或“只解析尾部”被误报成“物理上只读尾部” |
| 失败恢复 | 读取前边界不一致时保留上一份已验证 state，不把失败边界写成新基线；下一轮用新快照恢复时完整重读，并替换该来源的旧事件与旧审计行 | 一次失败让增量游标丢失，或恢复后把新旧版本混在一起 |
| 跨轮旧记忆隔离 | 旧记忆读取的工具调用只把不可逆 call-id 哈希写进 state；工具结果即使下一轮才追加，也会按哈希继续隔离 | 旧记忆调用和结果分处两轮时，结果被误当成当前事实 |
| 单写者与原子写入 | 会修改知识库的主要命令先取得同库独占锁；注册表使用自己的文件锁；结果用临时文件原子替换 | 两个 Agent 同时更新，把 review、索引、注册表或完成状态互相覆盖 |
| 增量语义复用 | `review-init --from-review` 只沿用事件数量、顺序和完整语义事件哈希相同的项目及仍有效记录；变化项目重新打开，跨项目关系重新检查 | 每次从零重读全部历史，或在事件内容已变时盲目沿用旧结论 |
| 原生分页断点 | `review-packet --start-event --max-events` 返回连续片段、完整语义哈希、边界和可复制的 `receipt`；review 中的 `reading_receipts` 必须无缝覆盖整条项目链 | 长项目链被截断、跳段或重复阅读后却假装“已经通读” |
| 对话蒸馏 | Agent 按顺序读完清理后的完整项目链，把意图变化、行动、证据和边界写成项目详录 | 退化成目录索引、关键词拼接或顺滑成功摘要 |
| 完成阶梯 | 把提出、设计、实现、产物生成、安装、启用、调用、自动测试、真实交互、用户接受、提交、合并、远端发布和公开可访问分别记录 | 把“写了代码”“测试通过”“已经上线”混为一谈 |
| 证据双向连接 | 关系需要两个项目各自的事件证据；图谱保留真实方向，两个文档都生成可返回入口 | 只凭文件名或关键词制造看似合理的知识关系 |
| 反馈驱动规则演进 | 正面、负面、缺口和结果反馈先成为有对象、有范围的记录，再进入候选、批准、版本和行为验证流程 | 一句临时意见被放大成永久人格或全局规则 |
| Reader 图谱白名单 | 只使用索引声明的图文件，核对图状态和 run id，并要求图中的文档节点与索引文档完全一致；archive 路径永远拒绝 | 被替换的默认图、图外文件或旧归档借关系边重新进入上下文 |
| 正负检索机器门 | 发布后必须用一个相关任务确认能命中，并用一个无关任务确认返回 `no_match`；失败就保持未完成状态 | Reader 看似能搜，实际总是漏掉相关内容或泛滥加载 |
| dry-run 与审计 | dry-run 不写正式知识库；正式运行记录文件/事件数量、排除、去重、脱敏、二进制、错误、回退、未知格式和扫描缺口 | 用户无法知道系统实际读了什么、丢了什么 |

## 对话蒸馏不是“帮我总结一下”

每个真实项目都保留七类信息：

| 项目字段 | 保存什么 |
| --- | --- |
| `objective` | 用户最初要解决的问题和当时语境 |
| `changes_and_corrections` | 后续增加、撤回、改口、否定和替代版本 |
| `actions_and_artifacts` | 实际执行过的动作与真正生成的产物 |
| `validation_and_observations` | 测试、浏览器、设备和工具观察覆盖到哪里 |
| `failures_and_fallbacks` | 报错、中断、失败尝试和回退带来的影响 |
| `delivery_and_state` | 会话结束时有直接证据支持的最高完成层级 |
| `remaining_work` | 尚未验证、尚未交付、仍有争议或需要确认的部分 |

每个重要断言都引用事件 id。Agent 自己说“完成了”只是 Agent 报告；补丁、测试、真实交互、用户验收和远端可访问是不同证据层。

## 双向连接怎样避免幻觉

文件名相似、目录相邻或关键词重合只能帮忙找候选，不能证明关系。确认一条连接时，要重新打开两个项目的完整证据包，并分别找到支持该关系的事件。

```text
knowledge-graph.json
项目 A  →  provides-foundation-for  →  项目 B

项目 A.md
相关知识  →  项目 B

项目 B.md
相关知识  →  项目 A（reverse of provides-foundation-for）
```

图谱中的因果或依赖方向不会因为生成了返回链接而反转。证据不足的候选保留为 `uncertain`，被否定的候选保留为 `rejected`，都不会进入正式导航。

## “自进化”在这里是什么意思

知识库不会因为收到了新反馈就立刻改写长期规则。完整链路是：

```text
原始反馈
  → feedback_signal：记录正面/负面/缺口/结果、对象和适用范围
  → rule_evolution candidate：提出可观察的规则候选
  → 批准门：明确的本人批准；或把跨项目重复证据发布为有范围的 confirmed 规则
  → rule_version：保留版本、旧规则和预期行为变化
  → approved：规则已获批准，但还没有证明效果
  → baseline_event_ids 与后续真实任务中的独立行为证据
  → validated：观察到预期改变，才称为已进化（evolved）
```

单次反馈默认只在该产物或项目内有效。全局候选需要明确的全局批准，或至少两个独立项目语境中的重复证据；即使获批，没有后续行为验证也只能叫“已批准、待验证”，不能叫“已经进化”。候选和被拒绝规则只作为非活动记录保留，不会渲染成当前行为规则，Reader 也不会执行它们。

## 增量更新怎样省时间

新一轮不会直接相信旧总结，也不会无条件重读全部历史。

- snapshot v2 只有在每个请求来源都取得 `frozen_sha256`、数量相符且没有 error 时才完整；`freeze` 只要一个来源失败就不写文件，手工留下的不完整 snapshot 也不能用于 rebuild。
- 完全没有事件、未知格式或扫描边界变化时，可以保留已经通过检索门的发布结果。
- 新增或变化的项目会失效并重新复核。
- 只有事件数量、有序事件 id 和完整事件内容哈希都相同的项目，才可以从上一份 review 复用；只要发生复用，就必须完成机器检查的 `cross_project_recheck`，重新核对引用变化项目的关系、冲突和规则。
- 原始 session 被截断、重写，或实际读取流的完整摘要与 snapshot 不一致时，不会推进旧 state。下一轮取得一致的新快照后会完整重读，并删除该来源的旧事件表示再写入恢复结果。即使大小、时间或采样边界看起来恢复，完整冻结摘要不匹配仍会拒绝。
- 旧记忆工具调用与它稍后追加的工具结果可以跨轮关联，但 state 只保存不可逆调用哈希，不保存原始 call id 或旧记忆内容。
- 增量只解析新尾部，不代表只从磁盘读取新尾部。旧前缀仍会为 append 完整性和实际读取流摘要被读取；`bytes_parsed` 与 `integrity_bytes_read` 分开审计。
- 每个来源的 `transport_records_seen/accounted/unaccounted` 在 state 中累计，下一轮没有新增记录也不会把以前的未说明分母清零。
- 私人工作目录只在内存中参与不可逆项目键计算；state 保存脱敏的项目身份映射，使后续尾部继续归入同一项目，又不保存原始私人路径。

这叫“复用仍然有效的证据结论”，不是让旧记忆覆盖新事实。

## 最终会生成什么

| 位置 | 内容 |
| --- | --- |
| `knowledge/00-evidence-rules.md` | 证据等级、阅读规则、隐私边界和完成状态标准 |
| `knowledge/01-identity-and-current-direction.md` | 有直接证据的身份、角色和当前方向，保留日期与范围 |
| `knowledge/02-collaboration-and-expression.md` | 已确认且有范围的协作/表达规则，以及已批准或已验证的规则版本 |
| `knowledge/projects/*.md` | 按真实项目链整理的详细过程史 |
| `knowledge/archive/<run-id>/` | 不再属于当前发布的旧版或改名项目文档；只作私人历史留存，不进入当前索引 |
| `knowledge/knowledge-graph.json` | 文档、结论、项目断言、反馈、规则版本和关系边 |
| `knowledge/knowledge-index.json` | Reader 使用的已发布索引与演进状态 |
| `review/` | 与当前事件集合哈希绑定的语义复核文件 |
| `audit/` | 统计、归属、排除、错误、回退、未知格式、关系候选、规则演进、当前发布文件、过期文档去向和检索验证 |

这些是普通 Markdown、JSON 和 JSONL 文件，不依赖某个笔记软件、数据库、向量库或外部索引服务。用户可以在明确理解隐私和同步边界后，再把已发布内容接入自己的工具；那不属于本 Skill 默认授权的动作。

`audit/published-files.json` 只记录“这次哪些生成文件属于当前发布”，用于下一轮发现旧路径；检索验证另有带大小和哈希的发布清单。旧项目文档被归档后不会继续出现在当前索引里，Reader 也不会拿归档文件兜底。

## 保存位置要由用户决定

知识库会包含私人记录。Rebuilder 在写入前必须展示选项并询问保存位置，不能默认放进 Skill 源码、公开仓库、session 原目录、整个用户目录或文件系统根目录。

- 私人本地目录最容易控制权限。
- 项目内目录只有在该项目本身私有、且不会被提交时才合适。
- 云同步目录可能把知识上传到第三方服务；共享目录还可能让团队成员或链接访问者看到内容。使用前应确认同步范围、共享权限、历史版本和备份策略。
- 还要根据 session 的敏感程度确认设备或磁盘加密、文件权限，以及备份是否会长期保留已经删除或替换的私人内容。
- 注册 Reader 只是写入一条本地位置映射，不等于上传，也不授予修改知识库的权限。

## 已实现并测试的输入格式

当前准确支持以下七种 session 格式：

1. Codex rollout JSONL
2. Clacky session JSON
3. Clacky chunk Markdown
4. Claude Code project JSONL
5. WorkBuddy project JSONL
6. Neo Claude-compatible project JSONL
7. Cursor `agent-transcripts` JSONL

排列只是在列出已验证格式，不表示某种输入、宿主或系统优先。其他格式会进入未支持报告。适配器契约和自动发现机制只说明可以继续扩展，不代表已经兼容所有 Agent。新增兼容声明需要真实样本、解析实现、合约测试和该精确格式的端到端样本验证。

## “兼容”必须分成三件事

| 兼容轴 | 证明什么 | 当前边界 |
| --- | --- | --- |
| 输入格式 | 某种精确 session 格式能被识别、解析、清理和冻结 | 只包括上面列出的七种已验证格式 |
| 执行宿主 | 某个 Agent 产品能发现、调用并完整执行两个 Skill 的语义流程 | 不能从“能读 `SKILL.md`”或“能运行 Python”自动推出；未逐一验证的宿主不作兼容声明 |
| 操作系统 | 完整流程在某类真实系统环境中跑通 | 路径和配置逻辑有多系统自动测试；真实格式端到端证据当前来自 macOS，不能据此声称所有系统均已实测 |

详细证据见[兼容矩阵](agent-session-knowledge-rebuilder/references/compatibility.md)。未知 Agent、未知版本、云端历史和不可访问账户必须继续写成未验证或不支持。

## 安装与运行条件

把两个 Skill 目录放到所用 Agent 能读取的 Skill 位置。宿主没有原生 Skill 发现机制时，也可以让它直接读取各自的 `SKILL.md`，但这不自动构成“该宿主已兼容”的证据。

运行确定性处理脚本需要 Python 3.9 或更高版本，仅使用标准库。Python 负责文件扫描、解析、清理、哈希、冻结、验证和审计；Agent 负责逐段语义阅读、意图判断和知识写作。缺少 Python 时，Skill 仍是一套说明文件，但无法可靠完成可重复的全量处理和机器门验证。

```bash
python3 agent-session-knowledge-rebuilder/scripts/session_kb.py --help
python3 agent-knowledge-reader/scripts/read_knowledge.py --help
```

原始 session 默认只读。任何安装运行时、扩大读取权限、上传、公开发布或注册 Reader 的动作，都需要各自相称的授权。

## 什么时候才算完成

`rebuild` 只代表确定性证据层生成完毕，`distill` 后仍是 `needs_retrieval_verification`。还必须运行一正一负两次检索：

```bash
python3 agent-session-knowledge-rebuilder/scripts/session_kb.py verify-retrieval \
  --kb /user-chosen/private/kb \
  --related-task "一个应该命中已发布项目的任务" \
  --unrelated-task "一个应该返回 no_match 的无关任务"
```

只有两道门都通过，完成报告才会进入 `complete` 或 `complete_with_unsupported_formats`，并记录当时已发布知识文件的清单哈希。之后如果文件被修改、替换或删除，Reader 和注册入口会拒绝旧验证结果。后一个完成状态只表示已知支持格式完成发布、同时保留了用户已确认的未知格式，不会把未知格式升级成兼容。
