# Agent Session 知识库重建

你和不同 Agent 做了很多项目以后，真正有用的信息会散在一条条 session 里。新的 Agent 能看到当前对话，却不知道某个项目为什么改过方向、哪次“已完成”后来又被推翻、最后真实验证到了哪一步，也不知道哪些第一人称其实来自客户、测试角色或第三方材料。

这套 Skill 会把这些 session 重新整理成一套可以继续维护和调用的知识库。

当前版本：**v0.3.3（Beta）**

```text
原始 session
  → 清洗并统一成可审计事件
  → 合并同一项目的续接会话
  → Agent 逐项目复核和蒸馏
  → 生成项目详录、基础知识与关系图
  → 后续任务只读取相关部分
```

## 对话蒸馏已经有了吗

有。

这里的蒸馏不会给每条 session 写一段顺滑摘要。程序先完整读取已支持的文件，保留用户消息、Agent 正文、工具调用与结果、补丁、浏览器和设备事件、错误、回退与真实交付，同时隔离压缩摘要、运行时注入、旧记忆、嵌套转录、隐藏推理和二进制正文。

续接 session 会先按原生会话 id、父子关系和项目线索合并。随后，正在执行 Skill 的 Agent 要按顺序读完每条清洗后的项目链，并整理这些内容：

- 用户最初要解决什么；
- 后来增加、撤回或纠正了什么；
- 实际做过哪些动作，生成过哪些文件；
- 测试、浏览器或设备究竟验证了什么；
- 哪些尝试失败，使用过什么回退；
- 最终交付到了哪一层；
- 还有什么没有完成。

每一条进入知识库的结论都要引用原始事件 id。复核文件会绑定本次运行和项目事件集合的哈希；源 session 增量变化以后，受影响的旧结论必须重新检查。项目没有全部复核、证据对不上、发现错误分组或仍有未处理格式时，发布门会直接拒绝通过。

这部分需要 Agent 做语义判断。只运行 Python 抽取命令会停在 `needs_semantic_review`，不会自动编造个人身份、项目因果或完成状态。

## 双向连接已经有了吗

也有。

项目详录稳定以后，Agent 会再比较不同项目之间的真实关系，例如续接、依赖、共同产物、交接、纠正或矛盾。一个关系必须同时引用两端项目的证据。文件名相似、目录接近或关键词重合只能用来寻找候选，不能直接建立连接。

例如，项目 A 产出了一个共享引擎，项目 B 的原始记录明确说继续使用这个引擎。通过复核后会产生下面的结果：

```text
项目 A ── continued-as ──> 项目 B
项目 A 的文章可以进入项目 B
项目 B 的文章也能返回项目 A
```

关系的真实方向保存在 `knowledge-graph.json` 中，两篇项目文档则各自生成可点击的正向链接和反向链接。不确定或已经否定的候选关系只进入审计文件，不会混进正式导航。读取 Skill 还能沿着少量已经确认的关系找到相关项目，不会顺着整个图把全部知识塞进上下文。

仓库中的契约测试已经验证：只靠关键词的关系会被拒绝；同时拥有两端证据的关系可以生成图边、两篇文档的互链，并在检索时带回一跳相关项目。

## 最终会得到什么

正式发布的知识库包含三类基础知识：证据与阅读规则、身份与当前方向、协作与表达规则。每个真实项目另有一篇详细历史，保留目标、纠正、动作、验证、失败、交付和遗留。知识图谱记录项目、结论和证据之间的关系，审计目录保存处理统计、排除原因、未知格式、错误、回退和未发布的关系候选。

仓库里的两个 Skill 分工如下：

- `agent-session-knowledge-rebuilder` 负责发现、读取、清理、蒸馏、连接和增量维护。
- `agent-knowledge-reader` 负责在新任务中读取少量已经发布的相关知识。没有匹配内容时返回 `no_match`。

## 已验证的 session 输入格式

当前已经实现并测试以下具体格式：

- Codex rollout JSONL
- Clacky session JSON 与 chunk Markdown
- Claude Code project JSONL
- WorkBuddy project JSONL
- Neo Claude-compatible project JSONL
- Cursor `agent-transcripts` JSONL

其他格式会明确报告为不支持。发现某个 Agent 的安装目录，或者仓库里存在适配器接口，都不能证明它已经兼容。详细证据等级见[兼容矩阵](agent-session-knowledge-rebuilder/references/compatibility.md)。

session 输入格式兼容、Agent 宿主能否自动发现 Skill、操作系统是否做过真实端到端验证，是三件不同的事，本仓库不会把其中一项的通过写成另外两项也通过。

## 怎么使用

需要 Python 3.9 或更高版本。程序只使用 Python 标准库，不需要额外安装 Python 包。原始 session 默认只读，不会被修改或删除。

在支持 Skill 的 Agent 中安装下面两个目录；具体放置位置和调用方式以该 Agent 自己的规则为准：

```text
agent-session-knowledge-rebuilder/
agent-knowledge-reader/
```

先让 Agent 加载 `agent-session-knowledge-rebuilder/SKILL.md` 并开始重建。它会先清点当前环境中能合法访问的 session；如果还没有指定知识库保存位置，它必须先把选项讲清楚并等待用户确认。抽取完成以后，Agent 继续逐项目复核、建立关系、校验并发布，不能把空白复核表丢给用户填写。

知识库发布后，让 Agent 加载 `agent-knowledge-reader/SKILL.md`。它会根据当前任务挑选相关基础文档和少量项目详录。

需要直接调用脚本时，可以先查看命令帮助：

```bash
python3 agent-session-knowledge-rebuilder/scripts/session_kb.py --help
python3 agent-knowledge-reader/scripts/read_knowledge.py --help
```

一个 Agent 能读取 `SKILL.md` 或运行 Python，不等于它已经完成宿主适配。未经过真实调用验证的 Agent 宿主仍要如实标为未验证。

## 隐私与安全

知识库是私人数据，不能写进这个公开仓库。重建流程会区分本人、未知用户、Agent、子 Agent、测试角色、客户角色和第三方材料；会清理常见凭据、Cookie、私人联系方式、私有网络地址、本机私人路径与 Base64 正文；也会避免在同一轮里重复读取自己刚生成的日志。

发布 Skill 源码前可以运行：

```bash
python3 agent-session-knowledge-rebuilder/scripts/session_kb.py release-check --root .
```

## 目前还没有做到的部分

- Windows 与 Linux 的发现路径有自动化测试，但真实格式的端到端验证目前来自 macOS。
- 语义上错误合并或错误拆分的项目链还不能自动改组；发现这类问题时必须停止发布并报告。
- 超大项目链使用连续检查点协议分段阅读，命令行暂时没有原生分页。
- 自动发现有明确扫描边界，不能承诺读取机器上的每一个角落。
- 读取阶段目前主要使用审核索引中的标题、别名、关键词和少量已确认的一跳关系。
